# 静默保活选项说明

> 面板位置：多开管家主界面 → **静默保活** 区域。
> 本文解释各选项做什么、默认为什么改成每天、什么时候该开「常驻」。

## 先说结论

| 选项 | 作用 | 默认 | 建议 |
|------|------|------|------|
| **调度：每天 / 每隔 N 小时** | 到点冷启动续一次 AutoAuthKey | **每天**（04:00 起各号错开 10 分钟） | 优先每天；别开太勤 |
| **精简保活** | 只把免扫密钥续上，不开游戏中心 | 关 | 日常保活建议开 |
| **记录授权结果** | 保活时 Frida 截服务端返回 | 关 | 想知道号有没有掉时开 |
| **启动与游戏中也记录授权** | 手动启动/游戏中也挂 Frida | 关 | 做寿命实验时开 |
| **关游戏后常驻轻量运行时** | 关游戏窗后不杀进程，藏窗压内存保 ilink 长连接 | 关 | 想长期在线、能接受每箱数百 MB 时开 |

已有 `keepalive.json` 里各箱已保存的 `interval` **不会被强制改写**；只有默认值和尚无单独策略的箱走「每天」。

---

## 为什么默认改成每天一次（qb15 vs qb4）

实测对照：

- **qb15**：闲置近 3 天、**0 次**冷启动续期，仍能免扫进游戏。
- **qb4**：每 2 小时冷启动续期，反而约一天就失效。

结论：免扫没有「必须每几小时滚一次」的硬门槛；**越勤冷启越容易把密钥滚断**。默认改成每天一次兜底即可；游戏开着或开了常驻时，到点只保存、不重启。

---

## 背景：保活到底在保什么

F 组扫码重放实验（见 `docs/服务端规则测试.md`）摸清了免扫链路：

- **扫码登录 = ManualAuth（cmdid 3453）**：一次性，靠手机签名换一把 AutoAuthKey，本地无法伪造/重放。
- **免扫续期 = AutoAuth（cmdid 3198）**：拿着 AutoAuthKey 滚动刷新。**只要这把 key 不被顶、没过期，离线/换机/重放都能继续在线。**
- **被顶 = key 作废**：同号在别处扫码后，重放旧 key 得到 `error=0 ret=-13`，只能重新扫码。

所以"保活"的本质，就是**定期把浏览器拉起来、让 ilink 做一次 AutoAuth，把 AutoAuthKey 往前滚**，不让它过期。跟有没有打开游戏画面毫无关系。  
「长期在线」更靠谱的方向是：**关游戏后别杀进程**，让 ilink 长连接接着跳，而不是更勤的冷启。

## 关游戏后常驻轻量运行时（ResidentKeepalive，1.4.3 起）

### 它做什么

勾上后，玩家关掉游戏窗时**不再整箱 `StopSoft`**，而是进入常驻态：

1. 存凭证  
2. 藏 QQ / 微信壳窗口  
3. 杀浏览器渲染进程 + `EmptyWorkingSet` 压工作集  
4. **保留** QQBrowser + WeChatAppEx 进程（会话挂在浏览器上；WeChatAppEx 就是游戏本体，卸掉就没长连接）

界面阶段文案：`常驻保活中（轻量）`。

| 操作 | 开关关（现状） | 开关开 |
|------|----------------|--------|
| 玩家关掉游戏窗 | 整箱停 | 进常驻：藏窗压内存，不 Terminate |
| 点界面「停止」 | 整箱停 | **仍整箱停** |
| 定时 refresh | 冷启动 | 箱内已有微信运行时 → `resident-skip` 只存凭证；否则仍按调度冷启 |
| 再点「启动游戏」 | 冷启 | 常驻进程还在 → 复开 GameUrl，看门继续 |

运行时若挂了：先试 `RuntimeOnly`，再试一次 `Full` 后藏窗；连续失败则记日志并停箱，下次需冷启（不弹扫码，除非探针抓到 `ret=-13`）。

### 「轻量」边界

每箱仍会占 **QQBrowser + WeChatAppEx** 内存（通常数百 MB 级）。靠藏窗和 EmptyWorkingSet 压工作集，**不能**卸掉 WeChatAppEx 还声称保长连接。多箱常驻的内存配额/自动休眠未做，可后续再加。

### 什么时候开

- ✅ 希望关游戏后免扫尽量别断、能接受后台占内存 → **开**。  
- ❌ 只偶尔玩、想省内存 → 关（关游戏仍整箱停；靠每天一次冷启兜底）。

## 精简保活（LeanRefresh）

### 它做什么

勾上后，到点保活时**只做最轻的拉起动作**，依次尝试三种精简启动候选，哪个先把 `tdi_account.txt` 的密钥换新就收工：

| 候选 | 含义 |
|------|------|
| `Blank` | 起浏览器但不加载任何页面 |
| `NoUrl` | 起壳子不带 URL |
| `RuntimeOnly` | 只把微信运行时拉起来 |

全程**不打开游戏中心页、不做 CDP 刷页/GameUrl 触碰**（代码里 `leanNudge=false`），所以比完整启动快、占资源少。

### 失败怎么办

三种精简候选都没能续上密钥，会**自动回退到完整启动**（`Full` 模式：开游戏中心 + CDP reload + 重试），兜底保证这轮保活不白跑。

### 什么时候开

- ✅ 只想维持免扫在线、省电省资源 → **开**。
- ❌ 想每次保活顺便验证游戏可正常进入 → 关（走完整启动）。

## 记录授权结果（ProbeAuth）

### 它做什么

勾上后，保活时在沙箱里挂一个 **Frida 只读探针**（`tools/lean-refresh/hook_watch.py`），截 ilink 的明文返回，把服务端的授权结果记进 `logs/qb1.log` 和 `frida-ilink-qb1.txt`。

| 日志里的返回 | 含义 | 你该做什么 |
|--------------|------|-----------|
| `error=0 ret=0` | 免扫续期成功 | 正常 |
| `error=0 ret=-13` | **已被顶，key 作废** | 重新扫码登录 |
| `error≠0` | 传输/网络层出错 | 查网络、重试 |

从 1.4.1 起，**只有抓到 `ret=-13` 才会把密钥永久登记作废**。没开探针或没抓到返回时，「凭证被清空 + 扫码页」只算疑似失效：先从金库还原再冷启一次，仍不行才提示扫码。

### 什么时候开

- ✅ 多开号、想及时发现谁被顶 → **开**。  
- ❌ 没装 Python/frida，或只想最省事 → 关（开了也会自动跳过）。

## 启动与游戏中也记录授权（ProbeAuthLive，1.4.2 起）

「记录授权结果」只管定时保活。勾上本项后：

- 手动启动在浏览器拉起**之前**就挂探针；进游戏后持续盯着（`live auth:` 日志 / `live-auth` 事件）。
- 箱内观测每 6 小时续开；抓到 `AutoAuth ret=-13` 确认作废。
- 主要给 `docs/服务端规则测试.md` **G 组**取证，平时可关。

## 组合建议

| 场景 | 每天 | 精简 | 记录授权 | 常驻 |
|------|:----:|:----:|:--------:|:----:|
| 日常省力 | ✅ | ✅ | ⬜ | ⬜ |
| 长期在线（能接受内存） | ✅ | 可选 | 可选 | ✅ |
| 排查被顶 / 寿命实验 | ✅ | 随意 | ✅（+ 启动也记录） | 对照用 |
| 环境没 Python/frida | ✅ | 随意 | ⬜ | 随意 |

---

## 一句话总结

扫码一次不能真正"永久在线"——免扫靠 AutoAuthKey 与（可选的）ilink 长连接；被顶就得重扫。在这个前提下：

- **每天一次冷启**兜底续期，别开太勤；  
- **常驻轻量运行时**关游戏后保长连接；  
- **精简保活**让冷启续期更省力；  
- **记录授权结果**让"号被顶了"不再静默失败。
