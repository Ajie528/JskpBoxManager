# 免扫码真实寿命实测：续期不是必需的，高频续期才是杀手

> 记录于 2026-11-24。起因：qb1 启动异常排查时，发现一个 97 天没任何活动的账号
> 仍能免扫登录，这与程序里「免扫寿命约 30 天、必须定期续期」的假设直接冲突。
> 本文是该冲突的实测结论。

## 一、结论摘要

| 结论 | 证据 |
|---|---|
| **AutoauthKey 没有寿命上限** | 宿主机 97 天零活动仍有效；qb3 等 19 天旧 key 同样有效 |
| **`psk.key` 不决定免扫期限** | 宿主机 psk.key 97 天没动，照样免扫成功 |
| **决定免扫的是三件套** | `kTdiKeyAutoauthKey` + `kTdiKeyAutoauthEncKey` + `kTdiKeyDeviceId` |
| **同一把 key 只能有一个活跃会话** | qb98 用 qb1 凭证登录成功后，qb1 被顶下线 |
| **高频续期会触发风控，把号永久废掉** | qb4 2 分钟重开 8 次 → 30 小时后 -13，且该号所有历史 key 一并失效 |
| **失效判据看响应头 uin** | 正常回显 uin；被废的号返回 `0` |

## 二、实测过程

### 2.0 批量对照：存放时长 vs 有效性（8 个样本）

用各号 `credential\history` 里最老的一份快照，逐一真实发送 AutoAuth：

| 号 | 存放时长 | 响应头返回的 uin | 结果 |
|---|---|---|---|
| 宿主机 | **97 天** | 25984987294363862 ✓ | ✅ `code=0` |
| qb3 | 19 天 | 25985011724681964 ✓ | ✅ `code=0` |
| qb2 | 19 天 | 25985012983767251 ✓ | ✅ `code=0` |
| qb9 | 19 天 | 25985015530340689 ✓ | ✅ `code=0` |
| qb8 | 19 天 | 25985015615256899 ✓ | ✅ `code=0` |
| qb10 | 17 天 | 25985015857410674 ✓ | ✅ `code=0` |
| qb1 | 15 天 | 25984986361252076 ✓ | ✅ `code=0` |
| **qb4** | **10 天** | **0**（认不出来） | ❌ **`code=-13`** |

**关键结论：存放时长与有效性完全无关。**
97 天的 key 有效，10 天的 key 反而失效。唯一失效的 qb4 不是因为「放久了」，
而是**整个号被服务端废掉了**。

判据在响应头：正常号会回显正确的 uin，qb4 回的是 `0` —— 服务端连账号身份都不认了。

## 三、qb4 为什么一天就过期

qb4 是与宿主机完全相反的样本：它被程序自己的高频重开搞死的。

### 3.1 时间线（2026-11-22，运行 1.5.60）

```
19:16:54  常驻：密钥已用 20.8h old (limit 3h) -> renew now
19:16:54  常驻：周期性续期 → 重开游戏以滚动 AutoAuthKey
19:18:57  常驻续期：窗口内没滚成（下个周期再试）
19:19:02  常驻：密钥已用 20.9h old (limit 3h) -> renew now     ← 2 分钟后又来
19:19:02  常驻：周期性续期 → 重开游戏
19:21:05  窗口内没滚成
19:21:10  又来
 ...（每 2 分钟一轮）
19:38:21  常驻续期：出现二维码 → key 已死，需要扫码
```

**统计：11-22 全天「周期性续期」513 次，「窗口内没滚成」512 次。**
19:xx 那一小时里 18 次。

### 3.2 后果

```
2026-11-21 19:35:15  扫码登录（qr-scan）
2026-11-21 22:27:40  换成 key 65693f4d
2026-11-23 04:59:57  key 65693f4d 退役（probe--13）    ← 只活了 30 小时 32 分
2026-11-23 08:27:13  -13
2026-11-23 14:12:54  -13
2026-11-23 20:06:04  -13
2026-11-24 01:42:49  -13
2026-11-24 08:20:02  -13
```

扫码后 30 小时就作废，之后每 6 小时重试全是 -13，此号至今需要重新扫码。

`profiles\qb4\credential\revoked.txt`：
```

```

### 3.3 与宿主机对照

| | 宿主机 | qb4 |
|---|---|---|
| 请求频率 | 97 天 0 次 | 1 天 513 次 |
| 结果 | key 一直有效 | 30 小时被作废 |

**这不是「密钥自然过期」，是突发高频请求被服务端判定为异常。**

程序里早有这个判断（`LaunchSession.cs:547-549`）：

> qb4 在 11-13 09:27 于 5 秒内连打 22 次 AutoAuth（全 -13），
> 这种突发密度本身就是风控特征，也是这个号反复被顶的推手之一。

1.5.61 加了失败退避（5 分钟 → 10 → 20 → 40 → 80 → 120 封顶），但 qb4 的凭证
是在 1.5.60 期间被搞死的，退避来得太晚。

## 四、对现有设计的修正建议

### 4.1 可以放宽的

| 当前策略 | 建议 | 依据 |
|---|---|---|
| 每天 03:45/05:45 定时协议续期 | 改为 **7~30 天一次**，或干脆不做 | 97 天不动仍有效 |
| 启动预检换钥（密钥 >5h 就换） | 门槛提到 **24h 以上**，或默认关闭 | 每次启动都烧一次额度，纯浪费 |
| 常驻每 6 小时重开游戏滚 key | 大幅延长，或改为只在游戏自然关闭时续 | 重开是最高风险动作 |

### 4.2 必须保留的

**失败退避**（1.5.61 已加）——这是防「高频打死号」的唯一保险，不能去掉。

### 4.3 仍需验证的问题

宿主机的 key 之所以 97 天有效，可能还有一个未排除的因素：
**它从没被别的设备顶过**。而 qb1..qb16 这些高频使用的号，历史上确实出现过 -13。

要彻底区分「放置不动的 key 能活多久」与「频繁使用的 key 能活多久」，
还需要一个长期观察样本：

- qb17（已用宿主机凭证建好）：保持不动，定期用只读探测检查有效性
- 观察周期建议 30 天起

## 五、附：配置穿透机制的实测澄清

`BoxSetup.cs:67-71` 里有这样几条：

```csharp
@"%Local AppData%\Tencent\QQBrowser\User Data\WXRuntime_Log",
@"%Local AppData%\Tencent\QQBrowser\User Data\WXRuntime_Log\mmkv",
@"%Local AppData%\Tencent\QQBrowser\User Data\WXRuntime_Log\WMPF",
@"%Local AppData%\Tencent\QQBrowser\User Data\WXRuntime_Log\web",
```

看起来 `%Local AppData%` 会展开成宿主机路径，导致所有沙箱共享同一份 `WXRuntime_Log`。
**实测结论：在正常配置下不会，但这套配置确实有隐患。**

### 5.1 正常号的实际行为（qb1）

```
qb1 沙箱内 WXRuntime_Log: C:\Sandbox\Ajie\qb1\...\WXRuntime_Log
  文件数 = 4291，合计 481 MB        ← 是真实独立的目录

psk.key 对比：
  qb1  沙箱: 148FD90D21BF61A5...
  宿主机    : 8B1E54003F193BBA...
  相同 = False                      ← 完全没有共享
```

原因是 Sandboxie 的匹配优先级：**具体路径（`C:\Sandbox\Ajie\qb1\...`）优先于
通配展开（`%Local AppData%\...`）**，所以号自己的目录生效，`%Local AppData%` 那几条
实际上没有命中。

### 5.2 什么时候会真的穿透（qb99 的教训）

排查过程中我建过一个测试沙箱 qb99，**因为复制脚本用了 `set`（覆盖）而不是 `append`，
把 qb99 自己的 `C:\Sandbox\Ajie\qb99\...` 路径丢了，只剩下 `%Local AppData%` 那几条**。
结果 qb99 直读了宿主机的 `WXRuntime_Log`，把宿主机那个账号
（uin `25984987294363862`，2026-06-29 扫码的）连同 `psk.key` 一起继承了过来，
并成功发起了 AutoAuth。

这就是「qb99 为什么会有别人的登录凭证」的完整答案：
**不是从任何金库复制，而是配置缺了沙箱自有路径后，穿透读到了宿主机的运行时目录。**

### 5.3 建议

`%Local AppData%` 这几条 `WriteFilePath` 在没有配套 `ClosedFilePath` 的情况下，
是一个「配置一旦不全就串号」的隐患。建议二选一：

1. 建箱时显式加上 `ClosedFilePath=%Local AppData%\Tencent\QQBrowser\User Data\WXRuntime_Log`
   把它挡死，彻底杜绝穿透；
2. 或在 `BoxSetup.ConfigureBox` 里对这几个路径做「存在自有沙箱路径就跳过」的处理。

## 六、风险提示

**同一把 AutoauthKey 只能有一个活跃会话。** 对任意一份凭证发起 AutoAuth 并成功后，
原来用这把 key 的会话会被顶下线。所以：

- 不要用正在游戏的号的凭证做探测
- 复制凭证到新沙箱前，要确认原号不在运行
- 本文所有的 `--send` 测试都在 qb1 未运行、且用历史快照（非当前 key）的前提下进行
