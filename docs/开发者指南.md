# 开发者指南（在其他电脑上开发 / 发版）

给在另一台电脑上改代码的人看：怎么拉代码、编译、调试，以及**推送后怎么自动发版**。
普通使用说明见仓库根目录的 [README.md](../README.md)。

---

## 1. 准备环境

| 软件 | 用途 | 安装 |
|------|------|------|
| Windows 10/11 x64 | 程序只支持 Windows | — |
| Git | 拉代码、提交 | `winget install Git.Git` |
| .NET 8 SDK | 编译 | `winget install Microsoft.DotNet.SDK.8` |
| GitHub CLI（可选） | 看 CI 结果、本地手动发版 | `winget install GitHub.cli`，然后 `gh auth login` |
| Python 3 + frida（可选） | 只有用 `hook` 命令或「记录授权结果」时才需要 | 装 Python 3 后 `py -3 -m pip install frida psutil pefile` |
| Sandboxie-Plus、QQ 浏览器 | 真正运行、调试沙箱功能时需要 | 见 README |

编辑器随意：VS Code / Cursor（装 C# Dev Kit）、Visual Studio 2022 都可以，解决方案是 `JskpBoxManager.sln`。

## 2. 拉代码

仓库：<https://github.com/Ajie528/JskpBoxManager>（需要仓库的写权限才能推送，找仓库所有者在 Settings → Collaborators 里加你）。

```powershell
# SSH（推荐，先把公钥加到 GitHub：Settings → SSH and GPG keys）
git clone git@github.com:Ajie528/JskpBoxManager.git
# 或 HTTPS（第一次推送时会弹登录）
git clone https://github.com/Ajie528/JskpBoxManager.git

cd JskpBoxManager
git config user.name  "你的名字"
git config user.email "你的邮箱"
```

## 3. 目录结构

```text
JskpBoxManager.sln
Directory.Build.props        版本号（发版只改这里的 <Version>）
CHANGELOG.md                 更新记录（会编进程序，也是 Release 的说明）
build.ps1                    打包：dist\JskpBoxManager-<版本>\ 和同名 zip
release.ps1                  发版（CI 自动调用；本地也能手动跑）
.github/workflows/release.yml  推送到 main 后自动发版
src/JskpBoxManager/
  App.xaml.cs                入口：无参数开界面；带参数走命令行（launch / refresh / hook ...）
  Core/                      业务逻辑：沙箱、启动看门、保活、凭证金库、Frida 观测等
  UI/                        WPF 窗口
tools/lean-refresh/          Frida 观测脚本（hook 命令和「记录授权结果」用，会打进发布包）
tools/probe-*.ps1            攻击力 / 内存定位的调试脚本
docs/                        研究记录和使用说明
```

## 4. 编译和调试

```powershell
dotnet build src\JskpBoxManager\JskpBoxManager.csproj -c Release
```

产物：`src\JskpBoxManager\bin\Release\net8.0-windows\win-x64\JskpBoxManager.exe`。

**数据目录**：程序默认把金库、日志、保活设置放在 exe 旁边。从 `bin` 目录运行时旁边是空的，可以用 `--appdir` 指到一个已安装的目录（里面有 `profiles\`、`logs\`）：

```powershell
$exe = "src\JskpBoxManager\bin\Release\net8.0-windows\win-x64\JskpBoxManager.exe"
& $exe status qb1 --appdir D:\JskpBoxManager-1.2.0     # 只读，最安全
& $exe launch qb1 --appdir D:\JskpBoxManager-1.2.0     # 会真的启动沙箱
& $exe hook qb1 --seconds 60                            # hook/lean 没给 --appdir 时会在上级目录自动找已安装的目录
```

注意：

- **不要让调试版和已安装的正式版同时操作同一个沙箱**（比如正式版的保活计划任务正好在跑），会互相干扰。调试前在正式版界面里把对应沙箱停掉。
- 命令行列表见 README「命令行」一节。界面版直接双击 exe 或 `& $exe` 不带参数。
- 打包测试（和正式发布的产物完全一样，单文件、自带运行时）：`powershell -ExecutionPolicy Bypass -File build.ps1`，产物在 `dist\`。

## 5. 绝对不能提交的东西

`profiles\`、`logs\`、`keepalive.json`、`paths.json` 等运行数据**含微信登录凭证**，已经写在 `.gitignore` 里。

- 不要用 `git add -f` 强行加这些文件；
- 不要把整个安装目录拷进仓库再提交；
- `dist\`、`bin\`、`obj\` 也不提交（发布包由 CI 生成）。

提交前看一眼 `git status`，出现 `profiles`、`credential`、`tdi_account`、`psk.key` 字样就停下。

## 6. 发版：推送即发布（CI/CD）

`.github/workflows/release.yml` 在**每次推送到 `main`** 时运行（在 GitHub 的 Windows 机器上）：

1. 编译检查；
2. 读 `Directory.Build.props` 的版本号，比如 `1.2.1`；
3. 如果 `v1.2.1` 这个标签**还不存在**：打包 → 在这次提交上打 `v1.2.1` 标签 → 创建 GitHub Release，说明取自 `CHANGELOG.md` 的 `## [1.2.1]` 一节，上传 `JskpBoxManager.exe`、`JskpBoxManager.exe.sha256`、`JskpBoxManager-1.2.1.zip`；
4. 标签**已存在**（版本号没改）：只做编译检查，不发版。

所以**改了代码但不想发版**，就别动版本号；**要发版**，按下面做：

### 发一个新版本

1. 改 `Directory.Build.props` 里的 `<Version>`。规则：只修 bug 加修订号（1.2.0 → 1.2.1）；加功能加次版本号（1.2.0 → 1.3.0）；不兼容的数据 / 用法变化加主版本号。
2. 在 `CHANGELOG.md` 最上面新增一节，标题格式必须是 `## [版本号] - 日期`，下面写 `### 新增` / `### 变化` / `### 修复`。写给用户看，说人话。
3. 提交并推送：

   ```powershell
   git add -A
   git commit -m "v1.2.1：一句话说明改了什么"
   git push origin main
   ```

4. 打开仓库的 **Actions** 页看 `release` 是否成功（约 3～5 分钟），或者：

   ```powershell
   gh run watch          # 跟踪最新一次运行
   gh release list --limit 3
   ```

5. 成功后各电脑上的程序打开时会提示「有新版本」，点一下就自动更新。

### 常见失败

| 现象 | 原因 / 处理 |
|------|------|
| `CHANGELOG.md 里没有 ## [x.y.z] 这一节` | 版本号改了但没写更新记录，或标题格式不对。补上再推一次 |
| 编译检查失败 | 本地先 `dotnet build ... -c Release` 修好再推 |
| `gh release create 失败` / 403 | 仓库 Settings → Actions → General → Workflow permissions 选 **Read and write permissions** |
| 推送后没有新 Release | 版本号没改（日志里会写「已经发布过，跳过」） |
| 想重发同一个版本 | 不要重发。改成下一个修订号再推 |

### 本地手动发版（CI 不可用时）

```powershell
gh auth login                      # 第一次
powershell -ExecutionPolicy Bypass -File release.ps1
```

它和 CI 做的事一样，只是在本地打标签并推送。CI 和本地**只用一种**，版本号相同时后执行的那个会自动拒绝。

### 不要改的约定

- Release 附件名 `JskpBoxManager.exe` 和 `JskpBoxManager.exe.sha256`：程序的自动更新（`Core/Updater.cs`）按这两个名字下载和校验，改名会导致所有电脑无法自动更新。
- 标签格式 `v版本号`：自动更新按「最新 Release」比较版本号。
- 不要在 GitHub 上手动把旧版本设为 Latest。

## 7. 多人协作建议

- 推到 `main` 的版本号一变就会发版，所以**改动较大时先在分支上做**：

  ```powershell
  git switch -c feature/xxx
  # ...改代码、提交...
  git push -u origin feature/xxx
  gh pr create --fill               # 开 PR，合并进 main 时才会触发发版
  ```

- 开始改之前先 `git pull`，避免两个人同时改同一个版本号。
- 提交信息沿用 `vX.Y.Z：说明`（发版提交）或直接写中文说明（普通提交）。
