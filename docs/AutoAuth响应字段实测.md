# AutoAuth 响应字段实测（能不能抓到？能，且已抓到）

> 采集于 2026-11-10，qb1（中华丨阿杰，uin=25984986361252076），本机 R7000P。
> 命令：`JskpBoxManager.exe autoauth-dump qb1`

## 一句话结论

**能抓，而且已经抓到了完整响应。** 但答案是否定的那半：**服务端不回传有效期 / 到期时间。**

AutoAuth 响应里唯一的时间戳是 `ilinkst_` 票据里的**签发时刻**（与本请求同秒），
没有任何「多少秒/多少天后过期」「有效期至某日」的字段。所以免扫寿命**只能靠实测统计**，
不可能从响应里算出来。

## 怎么抓的

之前抓不到，原因很具体：`ProtocolRenew.DumpUnknownFields` 写了却**从未被调用**——
它只是一段死代码，所以历史上一次 dump 都没产生过。现在三条路都接通了：

| 方式 | 用法 | 说明 |
|------|------|------|
| 显式抓取 | `autoauth-dump qb1` | 主动发一次 AutoAuth，完整 dump，成功后自动写回新 key |
| 环境变量 | `set JSKP_DUMP_AUTOAUTH=1` | 平时的续期 / 探测顺手留档 |
| 标记文件 | 程序目录放 `autoauth-dump.on` | 同上，但不用每次设环境变量 |

产物：

- `logs\qbN.autoauth-fields.txt` —— 追加，人读
- `samples\autoauth\<时间戳>-qbN.txt` —— 单份，便于与其它样本对照

**注意：dump 里有请求/响应/明文的完整十六进制，本地诊断用，不要外传。**

### 前置条件

沙箱必须已停。运行中的 `WeChatAppEx` 内存里握着旧 key，会把它写回文件，
导致这次换到的新 key 丢失（见 `mmtls直连可行性研究.md` 6F）。命令会自己检查并拒绝。

## 抓到了什么：完整结构

成功响应 1325 字节（含 wpkg 头）→ 解密后 1412 字节。逐层展开：

```
f1 = base 结果块 { f1=code(0)  f2=0 }
f2 = unified {
  f1 = 3
  f2 = session {                    ← 新凭证在这里
    f1  bytes[24]                   会话 key
    f2  bytes[24]
    f3  bytes[162]                  ★ AutoauthKey（写回 kTdiKeyAutoauthKey）
    f4  bytes[24]                   ★ AutoauthEncKey（写回 kTdiKeyAutoauthEncKey）
    f5  varint 4                    恒定小整数，不是时间
    f7  varint 8516934146771758352  64 位随机量，不是时间
    f8  bytes[16]                   固定头 c91c0000 00060000...
    f9  bytes[35]                   ★ ServerId（写回 kTdiKeyServerId）
    f12 text "ilinkst_..."          ilinkst 票据（见下）
  }
  f3 = { f1=uin  f2="...@im.ilinkapp_..." }     uin + im 地址
  f5 = 域名池 { longcloud / shortcloud / ilinkstreamquic + 各 5 组 IPv4/IPv6 }
  f6 = 路由表 { getplayablebaseconfforilink / getplayablelaunchdataforilink }
}
```

对照已知实现（`tools/mmtls_autoauth.py`、我们自己的 `ProtocolRenew.Exchange`），
`session` 里 3 / 4 / 9 就是我们一直在用的三个字段，全部正确解出。

### `ilinkst_` 票据（f12）

152 字符的 `ilinkst_` 前缀字符串，去掉前缀后是 urlsafe base64，解开是 108 字节 protobuf：

```
f1 = 25984986361252076              uin
f2 = bytes[16] c91c0000000600000000000000000000
f3 = bytes[48]                      与 session.f3 同款（key 派生？）
f4 = "ilinkapp_0600005ba4e935"      appId
f5 = 1794273946                     ← unix 秒，等于**本次请求那一刻**
```

关键判读：`f5` 与抓取时间**同秒**（实测 09:25:46 抓、`1794273946` 就是 09:25:46）。
所以它是**签发时间**，不是到期时间。

## 为什么可以断定「没有有效期字段」

做了三层核对，不是看漏：

1. **顶层 / base / unified / session 全字段已展开**，逐个标注了值域；
2. **递归扫全树所有 varint**，筛出落在 2020～2036 年区间的——只有 0 个；
3. **钻进了 `ilinkst_` 票据**（base64 套 protobuf，普通遍历进去不了），
   里面唯一的时间戳就是签发时刻。

也就是说：就算服务端有寿命概念，它也**没有告诉客户端**。
这和 `mmtls直连可行性研究.md` 里「AutoAuth 响应里没有任何有效期字段」的旧结论一致，
现在是第一次有**原始报文**可以佐证。

## 顺带确认的两件事

### 1. `base.f2` 不是错误信息

`base` 里除 `code` 外还有个 `f2`，成功样本里恒为 `0`（varint），不是 error_msg。
被拒样本（`-13`）尚未采到，等某个号失效时用 `autoauth-dump` 抓一次即可对照——
那才是真正有用的一份：能看出服务端拒绝时到底带了什么说明。

### 2. 三个已知码的语义

| code | 含义 | 本次是否命中 |
|------|------|--------------|
| `0` | 成功并轮换 | ✅（3 次全部成功） |
| `-2` | 凭证不可用 / 设备信息不匹配 | 未采到 |
| `-13` | 已被服务端作废（多设备顶号 / 过期） | 未采到 |
| `-14` | 会话 / 票据失效 | 未采到 |

失效样本才是排查 qb4 的关键——现在有工具了，下次失效时抓一份就能看出 `-13` 的真因。

| 09:25:46 | `4fbc054f` | `6409afb9` | ✓ |

四次都在 1～2 秒内完成，`srv` 长度 35～36，无异常。
（连抓多次是为验证判读与写回逻辑，不是常规用法——AutoAuth 是轮换语义，抓一次就换一把 key。）

### 抓取时发现并修掉的一个真 bug

第一次抓完后 `status qb1` 显示 **live 和 vault 不是同一把 key**：

```
live  key=21ac88deb38cb8a2  at=11-10 02:09:24    ← 旧的
vault key=6409afb92e3d609d  at=11-10 09:25:46    ← 刚抓到的
```

原因：`WriteCredential` 只写 `cred.Path`，而 `ReadCredential` 取的是「live 与金库中较新那份」。
live 比金库新时就只改了 live，金库留着旧状态；而启动时 `Ilink.Restore` 见「金库更旧」会把它推回 live，
**这次抓取等于白做，还让服务端那把新 key 变成孤儿**。

这与 1.5.38 修的历史凭据恢复是同一类错误（只写一份、另一份留着被轮换掉的 key）。
现在 `CaptureOnce` 会同时写 live 和 vault，写完再用 `Ilink.Live` 校验一次。
实测第 4 次抓取后两者一致（`22c1386d`）。

顺带把抓取也纳入轮换额度记账（`autoauth-capture`），否则「每号每天最多换 N 次」这条判据会漏掉抓取产生的轮换。

## 失败样本（`-13`）：qb4 / qb16 实测（2026-11-10 10:13）

成功样本看不出「为什么被判死」，所以专门等两个已经失效的号，抓了两次拒绝响应。

| 采集 | 沙箱 | 账号 | 旧 key | 结果 |
|------|------|------|--------|------|
| 10:13:44 | qb4 | 清沫丶 | `3d0a2ead` | `-13` |
| 10:13:49 | qb16 | 有很多寰球票 | `1d9eb733` | `-13` |

### 结构：比成功响应小两个数量级

```
成功：body 1325B  → 解密 1412B
失败：body  261B  → 解密   21B      ← 只够放一个错误码
```

解密后的明文，**两个号逐字节完全一致**：

```
0A0D 08F3FFFFFFFFFFFFFFFF01 1200   1204 2002 2A00
```

| 字段 | 值 | 含义 |
|------|-----|------|
| `base.f1` | `18446744073709551603`（int64 即 **-13**） | 错误码，protobuf 用补码表示负数 |
| `base.f2` | `0` | 成功样本里也是 0 |
| `unified.f4` | `2` | 待解（成功样本里没有 f4） |
| `unified.f5` | `0` | — |

### 结论

1. **服务端不说明拒绝原因。** `base` 里没有任何文本字段，没有 `error_msg`；
   也没有任何时间戳。整棵树上连一个落在合理时间窗内的 varint 都没有。
2. **`-13` 是统一的「这条链不能用了」，不区分原因。** qb4（被顶）和 qb16（另一台设备顶掉）
   返回的字节完全相同 —— 服务端没有告诉我们是因为「别处扫码」还是「自然过期」。
   → 程序里那句「多半是同一微信号在别处扫码顶掉」是**推断，不是服务端说的**，措辞上应该保持这个分寸。
3. **`-13` 之后就真的没有本地办法了。** 拿到这个 21 字节的响应，本地能做的只有：
   换历史 key 再试（可能命中别的分支）或重新扫码。没有任何可用信息能用来「修复」这把 key。

### 为什么两个号都被判死

结合前面的全机截面（qb4 链 1.9 天、qb16 链 2.4 天，而同机其它号 12～25 天），
以及本节「服务端不提供原因」这条事实，可以排除的假设是：

- 不是「密钥太老」——失效时 qb4 的 key 才 22 小时，qb16 也只有 46 小时；
- 不是「保活频率不当」——两号的每日 03:30 / 05:30 保活都执行过；
- 不是「服务端到期时间」——响应里压根没有时间字段。

剩下的可能是「这两个微信号在别处被使用过」，但**服务端不告诉我们**，
所以本地无法证实。要证实只能从账号侧观察（手机微信登录记录）。

## 复现步骤

```powershell
# 1) 确认目标沙箱是停着的
.\JskpBoxManager.exe status qb1

# 2) 抓一次（会真实轮换密钥，成功后自动写回）
.\JskpBoxManager.exe autoauth-dump qb1

# 3) 看报告
start .\samples\autoauth\
```

抓**失效样本**时，如果 live 已经被运行时清空了（`status` 显示 `live invalid`），
要显式指定金库那份，并且用 `--no-commit`（那把已经死了，写回没有意义）：

```powershell
$v = 'profiles\qb4\wmpf\ilink\default\tdi\ilinkapp_0600005ba4e935\0\6\tdi_account.txt'
.\JskpBoxManager.exe autoauth-dump qb4 --no-commit --from $v
```

`--no-commit` 只是防止在已知死 key 上做无谓写回；抓取本身仍会真实发一次请求
（这是唯一能让服务端明确回答「这把还能不能用」的方式）。
