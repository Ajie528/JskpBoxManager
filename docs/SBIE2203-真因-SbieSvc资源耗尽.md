# SBIE2203 与「游戏中心不进」的真因：SbieSvc 长时间运行后资源耗尽

> 记录于 2026-11-25。qb1 连续两天启动卡在游戏中心，SBIE2203 刷屏。
> 排查结论是 **Sandboxie 服务进程本身泄漏**，与程序代码、浏览器版本、凭证都无关。

## 一、现象

qb1 点启动后：

```
10:59:25  启动 QQ 浏览器
11:00:04  浏览器界面（不是扫码页）→ 等游戏...
11:00:09  界面 40 秒没等到微信 → CDP 刷新一次游戏中心
11:01:17  页面探测无响应（连续 10 次，标签页可能在后台被节流）
11:01:49  界面 90 秒没等到微信运行时 → 冷启动重开
```

同时 Sandboxie 消息日志刷：

```
25.11.2026 11:01:01.611  QQBrowser.exe: SBIE2203 与 Sandboxie 服务的通信失败: RPCSS_SXS
25.11.2026 11:01:01.860  Start.exe:    SBIE2203 与 Sandboxie 服务的通信失败: RPCSS_SXS
25.11.2026 11:01:05.586  SGTool.exe:   SBIE2203 与 Sandboxie 服务的通信失败: RPCSS_SXS
```

注意报错的不只是 QQBrowser，连 **Start.exe 自己**和输入法 SGTool 都在报。
这说明问题在服务端，不在某一个进程。

## 二、关键观测

### 2.1 沙箱内只有 2 个浏览器进程

手动用完整参数启动后，稳定观察到：

```
[15s] 进程=2 [mainx1, assistantx1] CDP=ALIVE
[30s] 进程=3 [mainx2, assistantx1] CDP=ALIVE
[45s] 进程=2 [mainx1, assistantx1] CDP=ALIVE
```

**没有任何 `--type=renderer` / `--type=utility`（network/storage/gpu）子进程。**

对比正常启动时（11-24 成功那次）应有 20+ 个子进程。

而 CDP 端口是通的、能列出页签，说明**主进程完全正常，只是无法创建子进程**。

### 2.2 主进程在正常写 profile

```
Default 目录下 Preferences_02 / History / Web Data 等都在持续写入
Local State 也在更新
20261125_qb_bin.log 0 字节（这个文件一直是 0，不是判据）
```

排除「浏览器根本没起来」。

### 2.3 微信运行时完全没启动

```
沙箱内 WXRuntime_Log\log\main_20261125.xlog  最后写入 10:57:34
而当前这次启动是 10:59:25 之后
```

说明微信运行时（WeChatAppEx）从未被拉起。这解释为「游戏中心页没有能力调起小程序」——
因为浏览器连 renderer 都建不出来，页面 JS 根本没跑。

### 2.4 RPC 本身是通的

```
沙箱里跑 cmd.exe  → 52ms 返回，正常
SandboxieRpcSs    → 被正确拉起（pid 46096）
Start.exe /listpids → 40~50ms，但返回空
```

所以 SBIE2203 不是「RPC 完全不工作」，而是**间歇性超时**——
沙箱进程在建子进程时调用 RpcSs 超时，被 Sandboxie 判失败。

### 2.5 服务进程本身异常（决定性证据）

```
重启前：
  pid  31932  SbieSvc   13 MB    4 线程   146 句柄
  pid  34140  SbieSvc  200 MB   65 线程   405 句柄   ← 异常

系统已连续运行 16 天（上次开机 2026-11-09 17:34）
```

**`SbieSvc` 正常应在 20MB 以内、线程 < 10。这里是 200MB / 65 线程。**

同一台机器上还观察到一次 10 个 `SandboxieCrypto` 实例同时存在（正常 1 个）。

## 三、结论

**根因：Sandboxie 服务进程（SbieSvc）长时间运行后内部资源泄漏，
显著提高了沙箱内「进程创建子进程」的失败概率。**

因果链：

```
SbieSvc 运行 16 天 → 内存/线程/句柄累积泄漏（200MB / 65 线程）
  → 沙箱内进程创建子进程时，RpcSs 调用容易超时
  → Chromium 建不出 renderer/network/gpu 子进程
  → 页面只剩空壳（主进程活着、CDP 通、但 JS 不执行）
  → 游戏中心页永远调不起小程序
  → 程序判定「没等到微信运行时」→ 冷启动重开 → 同样的坑
  → 同时 Sandboxie 刷 SBIE2203
```

### 重要修正：这是**间歇性**的，不是必然失败

2026-11-25 11:20 部署 1.5.64 后做验证，发现同一个泄漏状态下
（`SbieSvc` 仍是 200MB / 65 线程）**启动又成功了**：

```
11:21:17  启动 QQ 浏览器
11:21:40  游戏窗已确认（凭证已换新=True）
11:21:46  看门开始
```

而同一台机器上 10:48 / 10:51 / 11:00 / 11:01 那几次是失败的。

所以准确表述是：

> **SbieSvc 泄漏会显著提高子进程创建失败的**概率**，但不是每次必失败。**

这也解释了为什么现象看起来「时好时坏」、反复重试偶尔能进去——
不是程序的重试策略有效，而是碰运气撞上了服务还能正常工作的时刻。

推测失败概率与**同时运行的沙箱数量**相关（失败那几次机器上可能还有别的沙箱有进程），
但这一点没有做严格对照实验，仅作记录。

这也解释了为什么 1.5.62 加的「页面假死探测」能识别出问题
（日志里 `页面卡住 17 秒没有进展 资源=0 图=0/0` 就是空壳的特征），
但识别出来也没用——因为冷启动重开同样建不出子进程。

## 四、修复

**重启 SbieSvc 服务，或重启整台电脑。**

后者更彻底（能清掉 16 天累积的所有东西），且不需要单独考虑服务依赖。

### 为什么不能程序自己修

程序里 `BoxRuntime.WaitRpcReady` 只能检测 `listpids` 的耗时，
没法判断「SbieSvc 内存 200MB」这种服务端健康度。
而且重启服务需要管理员权限，程序本身不以管理员运行。

### 可以考虑的预防

1. **定期重启电脑**：最简单有效。观察下来 10 天以上就开始出问题。
2. **启动前健康检查**：已在 **1.5.64** 实现（`BoxRuntime.CheckSbieHealth`），
   每次预热前读 `SbieSvc` 的 WorkingSet 与线程数，超过 100MB 或 40 线程就在日志告警。
   只调 `Get-Process`，不需要管理员权限。
   注意告警**不代表一定启动失败**——泄漏状态下仍有成功概率（见「重要修正」一节），
   它的用途是解释「为什么有时进不去」并提示该重启了。
3. **不要在排查时反复强制停箱**：每次 `StopForce` / `Terminate` 都会让
   SbieSvc 处理一批进程清理，累积消耗。11-25 这天 qb1 被强制停了 5 次
   （10:44 / 10:47 / 10:50 / 10:58 / 11:01），可能加速了恶化。

## 五、排除项（逐个验证过，都不是原因）

| 怀疑点 | 验证 | 结论 |
|---|---|---|
| QQ 浏览器又升级了 | 22.4.7011.400，与 11-24 相同 | ❌ 非原因 |
| 沙箱缺 ReadFilePath | qb1 有 `ReadFilePath=…\22.4.7011.400` | ❌ 非原因 |
| 凭证失效 | 05:45 保活刚成功换过 key | ❌ 非原因 |
| `--no-sandbox` 参数 | 去掉该参数后行为完全一致 | ❌ 非原因 |
| 程序代码（1.5.63 改动） | 1.5.62 时 11-24 也是同样现象 | ❌ 非原因 |
| 页面假死（11-24 的判断） | 11-24 那次是资源数停在 8 条；这次是资源数=0、连 renderer 都没有 | ⚠️ 不同病因，同一症状 |

**注意最后一行的区别**，这是本次排查的重要修正：

- **11-24 那次**：页面 `readyState=complete`、资源 8 条不再增长 → 真的是渲染进程假死
- **11-25 这次**：页面资源=0、`游戏框子节点=-1`、根本没有 renderer 进程 → SbieSvc 建不出子进程

两者都表现为「卡在游戏中心」，但根因不同。1.5.62 的探测对前者有效（能通过关标签重开恢复），
对后者无效（重开也建不出子进程）。
