# 静默保活选项说明

> 面板位置：多开管家主界面 → **静默保活** 区域。
> 本文解释各选项做什么、默认为什么改成每天、什么时候该开「常驻」。

## 先说结论

| 选项 | 作用 | 默认 | 建议 |
|------|------|------|------|
| **调度：每天 / 每隔 N 小时** | 到点冷启动续一次 AutoAuthKey | **每天**（04:00 起各号错开 10 分钟） | 优先每天；别开太勤 |
| **保活时先用纯协议续期** | 不开浏览器，直接连微信服务器换 key，0.5 秒完成 | 关 | 想省资源、箱子平时停着 → 开 |
| **关游戏后常驻轻量运行时** | 关游戏窗后不杀进程，藏窗压内存保 ilink 长连接 | 关 | 想长期在线、能接受每箱数百 MB 时开 |

已有 `keepalive.json` 里各箱已保存的 `interval` **不会被强制改写**；只有默认值和尚无单独策略的箱走「每天」。

> 1.5.18 起移除「记录授权结果」「启动与游戏中也记录授权」（Frida 截 AutoAuth 返回）。
> 结论已经落地，继续挂着还会在扫码后多调一次 AutoAuth 反而进不去游戏。手动观测仍可用 `hook` 命令。
>
> 1.5.20 起移除「精简保活」：三个候选（Blank / NoUrl / RuntimeOnly）已被两次实测证伪，
> AutoAuth 必须由游戏中心页面触发。省资源的需求改由纯协议续期承担。

---

## 为什么默认改成每天一次（qb15 vs qb4）

实测对照：

- **qb15**：闲置近 3 天、**0 次**冷启动续期，仍能免扫进游戏。
- **qb4**：每 2 小时冷启动续期，反而约一天就失效。

结论：免扫没有「必须每几小时滚一次」的硬门槛；**越勤冷启越容易把密钥滚断**。默认改成每天一次兜底即可；游戏开着或开了常驻时，到点只保存、不重启。

---

## 背景：保活到底在保什么

F 组扫码重放实验（见 `docs/服务端规则测试.md`）摸清了免扫链路：

- **扫码登录 = ManualAuth（cmdid 3453）**：一次性，靠手机签名换一把 AutoAuthKey，本地无法伪造/重放。
- **免扫续期 = AutoAuth（cmdid 3198）**：拿着 AutoAuthKey 滚动刷新。**只要这把 key 不被顶、没过期，离线/换机/重放都能继续在线。**
- **被顶 = key 作废**：同号在别处扫码后，重放旧 key 得到 `error=0 ret=-13`，只能重新扫码。

所以"保活"的本质，就是**定期把浏览器拉起来、让 ilink 做一次 AutoAuth，把 AutoAuthKey 往前滚**，不让它过期。跟有没有打开游戏画面毫无关系。  

> **实测校正（1.5.4）**：关游戏窗那一刻，ilink 的 app 层会话就会 `AppSessionTimeout` 断开——「藏窗保住长连接」其实保不住会话。真正决定能不能免扫重进的，是那把 **AutoAuthKey 还在不在寿命内**。所以常驻的正确做法不是「让长连接一直跳」，而是**周期性重开游戏做真实 AutoAuth 把 key 往前滚**（见下）。

## 关游戏后常驻轻量运行时（ResidentKeepalive，1.4.3 起）

### 它做什么

勾上后，玩家关掉游戏窗时**不再整箱 `StopSoft`**，而是进入常驻态：

1. 存凭证  
2. 藏 QQ / 微信壳窗口  
3. 杀浏览器渲染进程 + `EmptyWorkingSet` 压工作集  
4. **保留** QQBrowser + WeChatAppEx 进程（会话挂在浏览器上；WeChatAppEx 就是游戏本体，卸掉就没长连接）

界面阶段文案：`常驻保活中（轻量）`。

| 操作 | 开关关（现状） | 开关开 |
|------|----------------|--------|
| 玩家关掉游戏窗 | 整箱停 | 进常驻：藏窗压内存，不 Terminate |
| 点界面「停止」 | 整箱停 | **仍整箱停** |
| 定时 refresh | 冷启动 | 箱内已有微信运行时 → `resident-skip` 只存凭证；否则仍按调度冷启 |
| 再点「启动游戏」 | 冷启 | 常驻进程还在 → 复开 GameUrl，看门继续 |
| **常驻期间（1.5.4）** | — | **每 6 小时自动重开一次游戏做真实 AutoAuth**，把 key 往前滚再藏回去 |

运行时若挂了：先试 `RuntimeOnly`，再试一次 `Full` 后藏窗；连续失败则记日志并停箱，下次需冷启（不弹扫码，除非探针抓到 `ret=-13`）。

**为什么要 6 小时续期（1.5.4 修复）**：免扫链自然寿命约一天。早期常驻只保 psk、不滚 key，还占着看门锁让每天那次冷启续期被跳过，于是关游戏约一天后 key 过期、再开就要扫码且不自愈。现在常驻自己每 6 小时真滚一次 key（远在寿命内）；只有真滚不动且弹出扫码页，才转「需要扫码」。

> 另：**别对常驻箱用「深度压缩内存（含游戏）」或旧的自动压内存**——把 `WeChatAppEx` 工作集清到近 0 会把心跳线程换出、拖断长连接。1.5.4 起「自动压内存」已改成只压 QQ 浏览器。

### 「轻量」边界

每箱仍会占 **QQBrowser + WeChatAppEx** 内存（通常数百 MB 级）。靠藏窗和 EmptyWorkingSet 压工作集，**不能**卸掉 WeChatAppEx 还声称保长连接。多箱常驻的内存配额/自动休眠未做，可后续再加。

### 什么时候开

- ✅ 希望关游戏后免扫尽量别断、能接受后台占内存 → **开**。  
- ❌ 只偶尔玩、想省内存 → 关（关游戏仍整箱停；靠每天一次冷启兜底）。

## 精简保活（已移除，1.5.20）

这个选项在 1.5.20 删除了。原因是它**已经被两个版本、两次实测证伪**：

| 候选 | 10-29 | 11-04 复测（v1.5.9） |
|------|-------|---------------------|
| `Blank`（about:blank） | 拉不起 WeChatAppEx | 同 |
| `NoUrl` | 同 | 同 |
| `RuntimeOnly` | 未见换钥 | 进程起来了（`wxPid=29244`），**120 秒内一次 AutoAuth 都不发**，密钥完全不变 |

结论是 **`AutoAuth` 必须由游戏中心页面触发**，光有 `WeChatAppEx` 进程不够。
所以这三个候选永远不会成功，开着只是让保活多花约 6 分钟反复停箱/启动，然后仍然回退 Full。

它想解决的问题现在由 **纯协议续期**取代（0.5 秒、不开浏览器、成功率 100%），见下一节。

> `LaunchMode.RuntimeOnly` 保留，但只用于「常驻模式下微信运行时挂掉后重新拉起」。
> `keepalive.json` 里残留的 `leanRefresh` 键会被忽略，保存时不再写回。

## 纯协议续期（ProtocolRenew）

### 它做什么

不开浏览器、不启动微信运行时，直接 mmtls 连 `longcloud.weixin.com` 发 AutoAuth（cmdid 3198），
拿回轮换后的新 AutoAuthKey，写回 live + 金库。单次约 **0.5 秒**，比冷启动快两个数量级。

入口：

- 主界面「⚡ 纯协议续期（不开浏览器）」按钮（单个沙箱）；
- 命令行 `JskpBoxManager.exe protorenew qbN`（`--dry` 只算不发）；
- 勾「保活时先用纯协议续期」→ 到点先试协议，成功就整个跳过冷启动。

### ⚠ 必须沙箱已停时续期

运行时（`WeChatAppEx`）内存里握着**旧** key。协议续期让服务端立刻作废旧 key 后，运行时会：

1. 按内存里的旧状态把 `tdi_account.txt` 覆写回旧 key；
2. 会话判失效 → **游戏窗直接消失**。

qb15 实测（11-05 15:11:59）：续期成功换到新 key，**2 秒后**就被写回旧 key，4 秒后游戏窗没了，
新 key 也随之丢失。

所以 1.5.19 起加了硬拦截：游戏窗 / 微信运行时 / QQ 浏览器任一在跑就**拒绝续期**并说明原因。
`protorenew --force` 可强行跳过（仅供排查）。保活里的协议续期天然只在冷启动分支之前跑，箱子停着才生效。

> 这个拦截只管**本机这个沙箱**。手机等其他设备在线时续期是安全的：
> qb1 实测（11-05 15:39）手机玩着游戏时续期，手机全程不掉线；被踢是之后 PC 进游戏时
> 游戏服提示「该账号在其他登录」。详见 `docs/mmtls直连可行性研究.md` 6G 与
> `docs/服务端规则测试.md` E2 组。

> 运行中想续期：先关游戏或停箱，续完再启动——新 key 会直接免扫进游戏。
> 续期成功后会在 `profiles\qbN\credential\protocol-renewed.json` 存一份快照；
> 万一 live 被写回**续期前的旧 key**，程序会自动写回新 key 并记 `key-restored` 事件
> （运行时自己合法换成第三把 key 时不会误纠正）。

### 什么时候开

- ✅ 号多、想让保活几乎不占资源，且箱子平时是停的 → **开**。
- ❌ 号常年挂着游戏不关 → 协议续期根本不会被触发，靠常驻/冷启动。
- ⚠ 协议续期被服务端回 `-13` / `-14` 时直接标「需要扫码」，不会再去白跑一次冷启动。

## 组合建议

| 场景 | 每天 | 协议续期 | 常驻 |
|------|:----:|:--------:|:----:|
| 日常省力（箱子平时停） | ✅ | ✅ | ⬜ |
| 长期在线（能接受内存） | ✅ | ⬜ | ✅ |
| 排查被顶 / 寿命实验 | ✅ | 随意 | 对照用 |

---

## 一句话总结

扫码一次不能真正"永久在线"——免扫靠 AutoAuthKey；被顶就得重扫。在这个前提下：

- **纯协议续期**最省资源，但只能对停着的沙箱做；
- **每天一次冷启**兜底续期，别开太勤；  
- **常驻轻量运行时**关游戏后保长连接。
