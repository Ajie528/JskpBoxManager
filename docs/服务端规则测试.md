# 服务端规则测试

目的：弄清 ilink 凭证（`tdi_account.txt` 的 AutoauthKey）在服务端的三条规则，用来决定保活频率，也决定「免扫」能做到多久。

| 规则 | 问题 | 现状 |
|------|------|------|
| 轮换 | 每次免扫进游戏，密钥是否换新 | **已确认**：同一 `Uin` 下 AutoauthKey、AutoauthEncKey、ServerId、psk 一起换（qb1，10/27 16:57 → 10/28 09:01） |
| 空闲失效 | 多久不打开会要求重新扫码 | **至少 10 天**：R7000P 的 qb2（6.8 天）、qb11（9.8 天）、qb3（10.1 天）空闲后都直接免扫成功（见 A 组结果） |
| 最长存活 | 一直保活，扫码后多少天仍会被要求重扫 | 未测出上限；见下方 **B 组样本（2026-10-29）**：同晚多数号续期成功，唯 qb1（中华丨阿杰）在密钥空闲约 10 小时后被服务端拒绝，**不是空闲时效** |
| 旧密钥 | 换新后旧密钥是否立刻作废；用了旧的会不会连新的一起作废 | **已测**：不立刻作废，用旧的也不会连带作废新的（见下方 D 组结果） |
| 多设备 | 同一微信在另一台电脑扫码，会不会踢掉这台 | **已确认**（见 C 组结果）：后扫码的设备顶掉先登录的设备，在线的 4 秒内被踢下线 |
| 手机微信 | 同一个号在手机微信里玩小游戏，会不会顶掉沙箱 | **不会**（用户实测「中华丨阿杰」）。PC 微信未测，步骤见下方 **E 组** |
| 身份 | `uin` 是什么 | **已确认**：由「微信号 + ilink 应用」决定，同一个号在两台电脑上 `uin` 相同；重新扫码只换密钥，`uin` 不变 |

## 数据怎么来

不用手动抄。新脚本会自动往 `logs\ilink-events.jsonl` 写事件（只有哈希和 ilink uin，没有明文密钥）：

- `key-rotated`：一次成功的免扫自动授权。`gapHours` = 距上一把密钥过了多久，也就是扛过的空闲时长。
- `scan-login`：同一个号重新扫码登录（`uin` 不变，期间出现过扫码页）。
- `new-identity`：沙箱里换了一个微信号（出现新 `uin`），或首次登录。
- `need-scan`：被要求扫码。`keyAgeHours` = 当时距上次成功授权过了多久。
- `key-revoked`：启动后运行时把凭证清空，即这把密钥被服务端拒绝。`keyAgeHours` = 这把密钥当时已空闲多久（以凭证文件最后写入时间计）。原因是被别的设备扫码顶掉，或过期；A 组样本只要保证期间没在别处扫码，就是过期。
  1.1.7 起还带 `chainDays` / `chainRenewals`：这条**免扫链**（从上次扫码起一路免扫换新）活了多少天、换新了多少次；`chainStartKnown=false` 表示链的起点早于事件日志，实际只会更长。
- `refresh`：一次静默保活的结果。开了「记录授权结果」时带 `auth` / `authRet` / `authMsg`（服务端对 AutoAuth 的原始返回）。

主界面选中沙箱后，「登录」一栏会显示 `免扫链：自 MM-dd HH:mm 扫码起已免扫 N 天，免扫换新 M 次`；`status qbN` 命令也会打印这一行。B 组看这个数字就行。

**导出**：双击程序目录里的 `导出登录观测报告.bat`，把 `logs\ilink-report.txt` 和 `logs\ilink-events.jsonl` 两个文件发过来。

## 测试步骤（在跑多开的那台电脑上）

### 准备

1. 把整个仓库拷过去（覆盖旧版），双击 `打开QQ多开管理.bat`。
2. 每个号启动一次：能免扫就会记一条 `key-rotated`，弹二维码就扫，会记 `new-identity`。
3. 选好分组（下面三组互不干扰，每组 1–2 个号即可）。

### A 组：空闲失效（已用现成样本测完：至少 10 天，见上方结果；以下是原计划）

1. 在管理器里**关掉**这几个号的保活。
2. 按递增间隔各打开一次，进游戏后就可以关：1 天 → 2 天 → 4 天 → 7 天 → 14 天。每次打开都会重置空闲计时，所以每一次都是一个独立样本。
3. 某次弹二维码时，**照常扫码**即可。脚本已经记下了 `need-scan` 和当时的空闲时长，扫完会记 `new-identity`。
4. 结论：最长成功的 `gapHours` 和第一次失败的 `keyAgeHours` 之间，就是空闲失效的阈值。

### B 组：最长存活（开保活，从不手动重扫）

1. 这几个号**开启**每天保活（默认每天 03:00 起，各号错开 10 分钟）。
2. 平时可以正常玩，但出现二维码前不要用其它方式重新扫码。
3. 报告里每个 `uin` 会显示扫码时间；一旦出现 `need-scan`，报告会算出「存活 N 天」。一直没有 `need-scan`，就说明至少能活这么多天。

对照结论：

- **不是「密钥空闲 ~10 小时就失效」**：同晚 qb4/qb5/qb8 空闲 9～11 小时都续期成功，qb6/qb7 约 24 小时也成功。
- **不是短会话导致凭证没写好**：qb1 16:45 已有 `game-ok, key` 写入；qb4 同样只玩约 3 分钟后停箱，凌晨保活仍成功。
- **不是程序误判**：保活时运行时确实把凭证清成无效（与 C 组被顶掉的表现一致）；金库里那把 `eaf73712…` 已登记进 `revoked.txt`，早上还原被跳过是预期行为。
- **qb1（中华丨阿杰）当天已两次被拒**（16:43 与 03:01），其它开保活的号同晚全部成功 → 更像是**这个号在别处又被扫码/授权顶掉**，或主号比小号更容易被多端作废；诊断包里**没有**第二台电脑的 `scan-login` 记录，具体是哪台设备顶的尚未钉死。
- 手机微信玩小游戏「不会顶掉」仍以既有用户实测为准；本次凌晨顶号更符合 **另一台 PC / 另一个沙箱扫码**，或未观测到的授权操作。

### C 组：多设备互踢（需要两台电脑）

1. 选一个号 X，在电脑 1 上已登录（能免扫进游戏）。
2. 在电脑 2 上新建或清除一个沙箱，用**同一个微信**扫码进游戏。
3. 回到电脑 1，关掉 X 再启动：直接进游戏 = 不互踢；弹二维码 = 后扫的会踢掉先扫的。
4. 两台电脑都导出报告发过来（报告里带电脑名）。

### D 组：旧密钥（已在本机 qb1 上测完）

2026-10-28，同一 `uin=25984986361252076`，用 `tools\probe-ilink-launch.ps1` 绕开脚本直接启动：

| 时间 | 放进沙箱的密钥 | 结果 |
|------|----------------|------|
| 10-27 16:57 | K1 `26edb47f`（扫码所得） | — |
| 10-28 09:01 | K1 | 免扫成功，换成 K2 `100f3fe2` |
| 10-28 09:20 | K1（已被 K2 取代 19 分钟，空闲约 16 小时） | **免扫成功**，换成 K3 `b6328b50` |
| 10-28 09:28 | K2（K3 已经从 K1 分支签发） | **免扫成功**（6 秒换成 K4 `6bc7109d`，8 秒出游戏窗） |

结论：

- 换新后旧密钥**不会立刻作废**，至少上两代在几十分钟内仍然有效；
- 用旧密钥登录**不会连带作废**已经签发的新密钥；
- 服务端看起来是「每把密钥各有有效期」，而不是「只认最新一把」。所以要扫码的主因更可能是**密钥年龄 / 空闲时长超限**，A、B 组的数据最关键；金库始终保存最新一把仍然必要（旧脚本可能还原的是几天前的密钥）。

#### 补测：另一个微信号的旧凭证

10/23 11:03 的 `uin=25985014377111195` 是**另一个微信号「清沫丶」**（另一台电脑上的 qb4）。本机 qb1 原来登的是它，10/27 改用「中华丨阿杰」的微信扫码。把这份旧凭证原样放回 `tdi_account.txt`，其余文件保持中华丨阿杰的状态（包括 `psk.key`）：

| 秒 | 观察 |
|----|------|
| 6 | 运行时把旧身份的文件重写一遍，密钥不变 |
| 13 | `tdi_account.txt` 变成无效（密钥被清空） |
| 15 | 文件变成**当前身份** `uin=25984986…` 的新密钥 K5，游戏窗口出现，**没有弹二维码** |

结论：

- 进的是中华丨阿杰，没进清沫丶。**只换 `tdi_account.txt` 切不了号，也测不出那把旧密钥是否还有效**，这次不能当作空闲失效的证据。清沫丶当时配套的 `psk.key` / `applet.db` 已在 10/27 换号时被覆盖，本机无法再测。
- **`tdi_account.txt` 不是唯一的凭证来源。** 运行时在写 `psk.key` / `tdi_account.txt` 之前，先写了 `Applet\cfcd2084…\data\2\applet.db`（`cfcd2084…` = MD5("0")，全局目录，**加密**数据库）和 `WMPF\mpfastload\mpkv.db`。它是从这些地方，或者从当前身份的 `psk.key` 恢复出当前身份的。
- 按用户分的目录名 = MD5(uin)：`bb5f2608…` = 旧身份，`0aad1579…` = 当前身份。

对备份的影响：免扫登录、以及登的是哪个号，取决于「`ilink`（含 `tdi_account.txt`、`psk.key`）+ 全局 `applet.db` + `mpkv.db` + `device_uuid_0`」这一整套。凭证守护现在把它们当作一组：保存、还原、历史快照都整组处理（`$IlinkCompanionRels`）。

#### 线索：清沫丶在本机 qb1 上失效

- 本机 qb1（清沫丶）最后一次成功授权是 **10/23 11:03**；**10/27** 打开时已经要求扫码（用户确认），中间约 4.2 天没打开。
- 同期，另一台电脑的 qb4 也登着清沫丶，并且开着「每 4 小时」保活。
- 所以有两种解释，目前分不开：
  1. **空闲失效 ≤ 约 4 天**；
  2. **多设备互踢**：清沫丶在另一台电脑持续续期，把本机这份会话顶掉了。
- 可以立刻区分的测试：中华丨阿杰 10/27 16:57 在本机重新扫过码，而另一台电脑的 qb1 早先也登着中华丨阿杰。**在另一台电脑上打开 qb1**：
  - 直接进游戏 → 不互踢，那么清沫丶更可能是空闲约 4 天失效；
  - 要求扫码 → 多设备会互踢（后扫码的顶掉先登录的）。

#### C 组结果（2026-10-28，另一台电脑 R7000P）

中华丨阿杰（`uin=25984986361252076`，两台电脑相同）：

| 时间 | 设备 | 事件 |
|------|------|------|
| 10-27 16:04 | R7000P qb1 | 最后一次成功授权 |
| 10-27 16:57 | 本机 qb1 | 同一个号重新扫码 |
| 10-28 08:50 | R7000P qb1 | 打开时要求扫码（旧脚本日志「waiting for QR scan」），沙箱凭证已被运行时清空 |
| 10-28 09:01–09:38 | 本机 qb1 | 多次免扫成功 |
| 10-28 09:57 | R7000P qb1 | 新脚本先从金库补回 10-27 16:04 的凭证，仍弹二维码，扫码后进游戏 |
| 10-28 10:17 | R7000P qb1 | 关掉再开，免扫成功 |

- R7000P 那份凭证当时只空闲了约 16.8 小时。而本机空闲 16 小时可以免扫，所以它失效的原因不是空闲，而是**本机 16:57 的重新扫码把它顶掉了**。
- 结合清沫丶的线索（R7000P qb4 在 10-27 08:47 扫码 → 本机 qb1 当天就要求扫码），同一个微信号**后扫码的设备会顶掉先登录的设备**。
- 被顶掉的表现：运行时把 `tdi_account.txt` 清成无效，弹「QQ浏览器授权申请」；从金库补回旧凭证也没用。
- **已确认方向（10-28 10:31，本机）**：
  - 本机 qb1 当时开着游戏。R7000P 09:57:37 扫码完成后，本机运行时在 **09:57:41**（4 秒后）收尾退出：依次写 `applet.db`、`mpkv.db`、`tdi_account.txt` 后不再有任何写入，游戏被踢下线。
  - 10:31 本机用探测脚本重新启动（不做金库还原）：第 6 秒凭证被清空，150 秒内没有游戏窗口，停箱时检测到扫码授权页。
  - 也就是说，是**后扫码的设备顶掉先登录的设备**，在线的会被服务端立刻推送下线，离线的下次启动时被拒。被顶掉的那把密钥连同金库里的备份都作废，只能重新扫码。
  - 还不知道：**免扫续期会不会也踢别的设备**。本机 09:01–09:38 免扫时，R7000P 已经被前一天的扫码顶掉，这几次说明不了问题。不过一个号只留在一台设备上用，这个问题就不重要了。
- 实际含义：**一个微信号只固定在一台电脑的一个沙箱里用**；换电脑就等于重新扫码，原来那台会失效。
- 脚本已据此改进（10-28 10:43 在本机被顶掉的 qb1 上实测）：启动 40 秒内识别出「密钥被服务端拒绝」，记 `key-revoked` 事件，登记到 `credential\revoked.txt`，直接进入等扫码；不再像 R7000P 早上那样先还原金库、等 60 秒、再冷启动重试。

#### A 组结果（2026-10-28，R7000P，旧版脚本）

| 沙箱 | 上一把密钥 | 本次免扫 | 空闲 | 结果 |
|------|-----------|----------|------|------|
| qb2 | 10-21 15:10 | 10-28 10:55 | 163.7h（6.8 天） | 免扫成功 |
| qb11 | 10-18 15:58 | 10-28 11:07 | 235.2h（9.8 天） | 免扫成功 |
| qb3 | 10-18 09:21 | 10-28 11:00 | 241.6h（10.1 天） | 免扫成功 |

结论：

- 空闲失效**至少 10 天**。每天保活一次绰绰有余；R7000P qb4 的「每 4 小时」没有必要。
- 实际会让号要求扫码的，主要是**同一个微信号在别的设备 / 别的沙箱扫码**（C 组已确认会顶掉），以及旧脚本把很旧的凭证覆盖回沙箱。
- 手机微信里玩同一个号**不会**顶掉沙箱（用户实测）。
- 回头看 R7000P 之前那批失效：qb8、qb9、qb10、qb12、qb13、qb14 在 10-19～10-20 失效时只空闲了 1～3 天，qb4（清沫丶）10-27 08:47 扫码、当天 13 点前就失效，都不是空闲失效，更可能是被别处扫码顶掉，或旧脚本回滚。
- **2026-10-29 再确认**：R7000P 开保活的 qb4～qb8 全部续期成功；唯 qb1（中华丨阿杰）在扫码后约 10 小时的凌晨保活被 `key-revoked`。同空闲量级的其它号都没事 → 再次说明「很快要扫码」优先查**多设备互踢 / 主号被别处授权**，不要先怀疑保活间隔或空闲时效（详见上方 B 组样本）。
- **2026-10-29 精简保活试验（qb1）**：去掉 GameUrl（Blank/NoUrl）不会拉起 WeChatAppEx；直接启 WeChatAppEx 也未见 AutoAuth 换钥。同日用 Full 对照时该号密钥再次被服务端清空。详见 [`docs/mmtls直连可行性研究.md`](mmtls直连可行性研究.md)「精简保活实验结果」。

另外：R7000P qb7 的沙箱里有 10-28 04:03 的新密钥，金库里还是 10-27 15:45 的旧密钥（旧脚本保活失败后回滚造成）。新脚本下次启动时会先把沙箱里的新密钥收进金库。

注意：本机 10-28 09:25–09:40 那几条 `key-rotated` 是旧密钥测试产生的，`gapHours` 没有参考意义。R7000P 10-28 09:57:42 那条 `key-rotated` 其实是扫码登录，新版报告会根据日志自动改判为 `scan-login`。

注意：**不要在沙箱之间、或给同一个沙箱换号时只拷 `tdi_account.txt`**。要换号就用「清除登录」后重新扫码。

### E 组：PC 微信打开同一个游戏，会不会顶掉 QQ 浏览器（两台电脑）

要回答两个不同的问题，别混在一起：

- **游戏被挤下线**：游戏里弹「账号在别处登录」之类。这是游戏服务器限制同时在线，微信凭证没坏，重开还能免扫。
- **凭证被顶掉**：微信把 QQ 浏览器这边的授权作废，下次要扫码。这才影响保活。

设定：R7000P 的 qb1 用 QQ 浏览器（启动器）玩「中华丨阿杰」；本机（AJIE）用 **PC 微信**（登录同一个号）打开「向僵尸开炮」小游戏。

准备（R7000P）：

1. 更新到 1.1.7 或更高（发布包自带 `tools\lean-refresh`）。
2. 装 Python 3，执行 `py -3 -m pip install frida psutil pefile`。
3. 本机 qb1 也登着这个号。R7000P 扫码会把本机 qb1 顶掉（C 组结论），测试期间本机 qb1 不要启动，也先别开它的保活。

步骤：

1. **R7000P**：启动器启动 qb1，弹二维码就扫，进游戏。记下时间 T0。
2. **R7000P**：游戏开着，另开一个命令行窗口，在安装目录执行（不重启，盯一小时）：
   ```text
   JskpBoxManager.exe hook qb1 --no-launch --no-stop --seconds 3600
   ```
   看到 `[attach] ... role=ilink` 说明已挂上。
3. **本机**：PC 微信打开「向僵尸开炮」，进到游戏主界面。记下时间 T1。
4. **R7000P**：看 1～2 分钟：
   - 游戏有没有弹窗、弹窗原话（截图）；
   - 命令行有没有出现 `Logout` / `kick` / `SessionTimeout` / `TdiCheckCgiResponse` 之类的关键行。
5. 本机 PC 微信的游戏可以关掉了。R7000P 等 hook 结束，或者直接关掉那个命令行窗口。
6. **R7000P 验证凭证（最关键）**：关掉 qb1 的游戏，然后执行
   ```text
   JskpBoxManager.exe hook qb1 --seconds 60
   ```
   最后的「授权结果」：
   - `成功 AutoAuthResponse error=0 ret=0` → PC 微信**不会**顶掉 QQ 浏览器的凭证；
   - `失败 ... ret=非0 msg=...` → **会**顶掉，并且拿到了服务端拒绝时的 `ret` / 原因（第一份失败样本）。

要发过来的文件（R7000P 的安装目录下）：`logs\frida-ilink-qb1.txt`、`logs\frida-ilink-qb1.jsonl`、`logs\qb1.log`、`logs\ilink-events.jsonl`，以及 T0、T1 和弹窗截图。

可选加测：步骤 6 成功后，再在本机 PC 微信里打开一次游戏，这次 R7000P **不开游戏**（离线），隔几分钟后在 R7000P 再做一次步骤 6，看离线时会不会被顶。
